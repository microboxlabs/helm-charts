# MIOT Modulith Chart

A Helm chart for deploying **MIOT Modulith** - the ModularIoT Quarkus modulith backend for fleet, driver, tracking and resource management.

## Overview

MIOT Modulith is a modular monolith built with Quarkus. Each component is independently toggleable at deploy time via feature flags:

- **Fleet** - vehicle monitoring, trips, routes and geofences
- **Tracking** - GPS asset position ingestion via pluggable messaging (Pulsar or standalone)
- **Symptoms** - in-process dispatcher: CDC → RouteTable → optional SQL function / webhook
- **Trips** - mandates, trips, stages, cargo and resource assignments
- **Reactive + JDBC dual datasource** - Hibernate Reactive Panache for runtime queries, JDBC for Flyway migrations, both targeting the same PostgreSQL instance
- **Dual JWT authentication** - HS256 for M2M device endpoints, RS256 (JWKS) for web application endpoints, both from the same Auth0 tenant
- **Pluggable messaging** - log mode (standalone, no broker) or Pulsar for production
- **Prometheus metrics** and Quarkus health endpoints included out of the box

## Prerequisites

- Kubernetes 1.19+
- Helm 3.0+
- PostgreSQL database (external)
- Auth0 tenant with M2M API (HS256) and web API (RS256)
- Apache Pulsar (optional, only when `messaging.type=pulsar`)

## Installation

### Add the Helm repository

```bash
helm repo add mbl-charts https://microboxlabs.github.io/helm-charts
helm repo update
```

### Install with default configuration

```bash
helm install miot-modulith mbl-charts/miot-modulith
```

### Install with custom values

```bash
helm install miot-modulith mbl-charts/miot-modulith -f values.yaml
```

### KEDA Parameters

Requires KEDA in the cluster (`keda.sh/v1alpha1`). When `keda.enabled` is true, the chart renders a `ScaledObject` for its Deployment and the Deployment has no `spec.replicas`. Rendering fails if `autoscaling.enabled` is also true, or if `keda.triggers` is empty.

| Parameter | Description | Default |
|-----------|-------------|---------|
| `keda.enabled` | Render a KEDA `ScaledObject` | `false` |
| `keda.minReplicas` | `minReplicaCount` | `1` |
| `keda.maxReplicas` | `maxReplicaCount` | `5` |
| `keda.pollingInterval` | Seconds between trigger checks | `30` |
| `keda.cooldownPeriod` | Seconds after the last active trigger before scaling to 0 (only with `minReplicas: 0`) | `300` |
| `keda.behavior` | HPA behavior, rendered as `advanced.horizontalPodAutoscalerConfig.behavior` | `{}` |
| `keda.triggers` | KEDA triggers, rendered as given | `[]` |

**Prometheus trigger**

```yaml
keda:
  enabled: true
  minReplicas: 1
  maxReplicas: 5
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://prometheus.monitoring:9090
        query: sum(pulsar_subscription_back_log{topic="persistent://<tenant>/<namespace>/<topic>",subscription="<subscription>"})
        threshold: "1000"
        activationThreshold: "100"
```

KEDA sets the replica count to the query value divided by `threshold`, rounded up, within `minReplicas` and `maxReplicas`. With `minReplicas: 0`, KEDA scales to 0 while the value is at or below `activationThreshold`.

## Symptom Engine Instance

The `modulariot` umbrella chart can deploy this chart a second time under the alias `miot-symptoms-engine`. It uses the same image as `miot-modulith` and runs as a separate Deployment, usually with more replicas and only the symptoms component.

Enable it:

```yaml
miot-symptoms-engine:
  enabled: true
```

With the umbrella defaults the engine:

- runs 2 replicas (`replicaCount`, `autoscaling.*` for an HPA, or `keda.*` for a [KEDA ScaledObject](#keda-parameters))
- has no Service, Ingress, ApisixRoute or ServiceMonitor (`service.enabled: false`)
- turns on only `components.symptoms`
- disables the Quarkus Flyway extension's startup migrations and does not set OIDC env vars

The current image also runs a programmatic `FlywayMigrator` for active database-backed components, including symptoms. It does not honor `flyway.migrateAtStart`, so the engine still needs migration privileges. Apply schema changes before starting the engine. Running it with a database account without migration privileges requires an application image with a separate switch for the programmatic migrator; this chart cannot provide that switch for existing images.

All resources are named `<release>-miot-symptoms-engine`, so they do not clash with `<release>-miot-modulith`. The engine takes every parameter on this page under the `miot-symptoms-engine` key. Values set under `miot-modulith` are not copied. Set database, auth, messaging and symptoms values for the engine as well:

```yaml
miot-symptoms-engine:
  enabled: true
  replicaCount: 3
  resources:
    requests:
      cpu: 250m
      memory: 512Mi
  postgresql:
    external:
      host: postgresql.example.svc
      database: miot
      username: miot
      existingSecret: miot-db
  symptoms:
    # This ConfigMap must exist before the engine Pods can start.
    # Set non-empty miot-modulith.symptoms.routes and leave that instance's
    # existingRoutesConfigMap empty to have the umbrella create it.
    # For engine-owned routes, remove existingRoutesConfigMap and set routes.
    existingRoutesConfigMap: <release>-miot-modulith-symptoms-routes
    pulsar:
      serviceUrl: pulsar://pulsar.example.svc:6650
      topic: persistent://tenant/namespace/cdc-topic
      subscription: miot-symptoms-dispatcher
```

To also run trips in the engine, set `components.trips.enabled: true`. A `rule_id` must have one owner: when the engine runs symptoms, turn `components.symptoms` off in `miot-modulith`. For fork filters, `fork.existingFiltersConfigMap` mounts an existing ConfigMap at `/config/fork` in the same way.

## Upgrading

### To 0.8.0

- **New:** `keda.*` renders a KEDA `ScaledObject` (default off). See [KEDA Parameters](#keda-parameters).

### To 0.7.0

- **New:** `service.enabled` (default `true`). Set `false` for an instance that takes no HTTP traffic.
- **New:** `symptoms.existingRoutesConfigMap` and `fork.existingFiltersConfigMap` mount an existing ConfigMap.
- The `modulariot` umbrella pins the primary instance's `chartLabelVersion` to `0.6.2`, preserving existing manifests byte-for-byte when the engine is disabled. The package/dependency version remains `0.7.0`. Standalone installs use the package version in `helm.sh/chart` unless `chartLabelVersion` is set explicitly.

### To 0.3.0

- **New:** `components.tracking` for GPS asset tracking module
- **New:** `auth` section replaces `oidc` for dual JWT authentication (HS256 + RS256)
- **New:** `messaging` section for pluggable external messaging (log/pulsar)
- **Deprecated:** `oidc` section — OIDC env vars only render when `oidc.authServerUrl` is set. Migrate to `auth` section.
- **Breaking:** The Quarkus backend no longer includes `quarkus-oidc`. Existing deployments using OIDC must switch to the `auth` section with Auth0 credentials.

### To 0.x

This is the initial release. No upgrade notes.

## Troubleshooting

### Pod fails to start with database connection error

1. Verify the PostgreSQL service is running and accessible
2. Check the database credentials in the secret
3. Ensure the database `miot` exists

```bash
kubectl logs -l app.kubernetes.io/name=miot-modulith
```

### Authentication errors (401)

1. Verify `auth.hs256Issuer` matches the `iss` claim in your M2M tokens and `auth.rs256Issuer` matches the `iss` claim in your web tokens
2. For M2M (HS256): check that `auth.hs256Secret` matches the Auth0 API Signing Secret
3. For web (RS256): verify `auth.jwksUrl` is reachable from the cluster
4. Check audience values match the Auth0 API identifiers

```bash
# Test from local machine
kubectl port-forward svc/<release-name>-miot-modulith 8180:8180

# Get an M2M token and test
TOKEN=$(curl -s --request POST --url https://auth0.example.com/oauth/token \
  --header 'content-type: application/json' \
  --data '{"client_id":"...","client_secret":"...","audience":"...","grant_type":"client_credentials"}' | jq -r '.access_token')

curl -H "Authorization: Bearer $TOKEN" http://localhost:8180/api/v1/asset/track
```

### Health checks failing

1. Check if Flyway migrations completed successfully (set `flyway.migrateAtStart: true` and review logs)
2. Verify database connectivity
3. Review application logs for startup errors

```bash
kubectl port-forward svc/<release-name>-miot-modulith 8180:8180
curl -s http://localhost:8180/q/health
```

### Metrics not appearing in Prometheus

1. Verify the ServiceMonitor is created: `kubectl get servicemonitor`
2. Check that the ServiceMonitor labels match your Prometheus selector
3. Verify the metrics endpoint is accessible: `curl <pod-ip>:8180/q/metrics`
