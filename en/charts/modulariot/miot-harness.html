miot-harness Chart

A Helm chart for deploying MIOT Harness — the multi-agent FastAPI backend that powers ASK MIOT (miot_harness/api/server.py). Runs in its own cluster (separate from the datasource DB) and reaches it via private connectivity (VNet peering, Private Link, PostgREST, or a kubectl port-forward sidecar for dev).

Since chart 0.3.0 the configuration surface follows the harness’s datasource-agnostic refactor (modulariot#604 ): the core no longer hardcodes Nexo. datasource.kind selects a DataSourceProvider (currently nexo), and domain defaults — tenant lock, freshness gates — live in the provider’s profile, not in the chart. If you’re upgrading from 0.2.x, see Migrating to 0.3.0.

Overview

The miot-harness chart deploys:

  • FastAPI process on :8000, exposing /health and /runs.
  • Read-only-rootfs container, runs as UID 65534.
  • Credential channels (datasource DSN, Anthropic / OpenAI / Google API keys, Langfuse keys, identity signing key) with existingSecret-first precedence and a chart-managed Secret fallback for dev. All projected via secretKeyRef, never literal Pod env values.
  • Optional NetworkPolicy (default off) — DNS, public HTTPS, datasource-DB CIDR allowlist.
  • Optional tunnel sidecar (default off) — kubectl port-forward inside the Pod for dev environments.
  • Optional ServiceMonitor for Prometheus-Operator scraping of /metrics.
  • Optional PVC for run_store survivability (defaults to emptyDir).

Configuration conventions

The chart keeps your values files slim with two rules:

  1. Keys with a concrete default (e.g. env, datasource.kind) are always rendered as env vars.
  2. Keys defaulting to null are rendered only when you set them. Unset means “use the harness built-in default” (or the datasource provider’s profile default). The chart never re-states application defaults, so it can’t drift from them — and your environment values file only contains what actually differs.

Explicit falsy overrides are honored: agents.synthesizerStream: false and agents.synthesizerThinkingBudget: 0 render "false" / "0".

Prerequisites

  • Kubernetes 1.19+
  • Helm 3.0+
  • (Optional) Prometheus Operator if metrics.serviceMonitor.enabled=true.
  • (Optional) A CSI driver / storage class if persistence.enabled=true.
  • (Optional) A CNI that enforces NetworkPolicy if networkPolicy.enabled=true (Calico, Cilium, etc.).

Installation

Standalone

helm install harness microboxlabs/miot-harness \
  --namespace miot-harness \
  --create-namespace

As part of the modulariot umbrella

helm install platform microboxlabs/modulariot \
  --namespace modulariot \
  --set miot-harness.enabled=true

The umbrella defaults miot-harness.enabled: false so existing platform installs don’t suddenly get an agent runtime — opt in per environment.

Writable custom instructions and skills

Set contextSkills.writable=true to load custom instructions from /app/.miot-workspace/context and skills from /app/.miot-workspace/skills. An init container seeds both directories with the defaults packaged in the Harness image. It copies only missing files, so operator changes are not overwritten during an upgrade.

ParameterDescriptionDefault
contextSkills.writableRead context and skills from writable workspace directoriesfalse
contextSkills.seedDefaultsSeed missing packaged defaults with an init containertrue
contextSkills.initContainer.resourcesSeeder resource requests/limits{}

For durable customizations, enable both features:

contextSkills:
  writable: true
persistence:
  enabled: true
  size: 1Gi

The files are loaded at process startup; restart the Deployment after editing them. The default claim is ReadWriteOnce, which is appropriate for the default single replica. Select a ReadWriteMany storage class and access mode before scheduling multiple replicas on different nodes.

Example configurations

A copy-ready version of the production template lives in the repo at charts/miot-harness/examples/values-prod.yaml.

Production — slim template

Everything not listed falls back to chart defaults (deployment shape) or harness/provider defaults (tuning knobs). This is the full set of decisions a prod deploy actually has to make:

env: "prod"
defaultTenantId: "<your-tenant>"
defaultUserId: "service"
 
# Front-door auth — all three fields required once enabled.
auth:
  enabled: true
  issuer: "https://<your-tenant>.auth0.com/"
  jwksUrl: "https://<your-tenant>.auth0.com/.well-known/jwks.json"
  rs256Audience: "<auth0-web-app-client-id>"   # `aud` of the forwarded JWT
 
# DSN comes from an out-of-band Secret (key: dsn). Tenant lock and
# freshness gates are NOT set — the nexo profile supplies
# mintral / 30 / 240. Override datasource.tenantLock only if your
# front door injects a different tenant id.
datasource:
  existingSecret: "harness-datasource"
 
# Required: all default models + the intent router are claude-*.
anthropic:
  existingSecret: "harness-anthropic"   # key: api-key
 
# Tracing (optional — delete this block to run without it).
observability:
  otel:
    enabled: true
    endpoint: "http://otel-collector.observability:4317"
  langfuse:
    host: "https://<your-langfuse-host>"
    existingSecret: "harness-langfuse"  # keys: public-key, secret-key
 
resources:
  requests:
    cpu: 500m
    memory: 1Gi
  limits:
    memory: 2Gi
 
persistence:
  enabled: true
  size: 10Gi

Create the referenced Secrets out-of-band (or via your secret operator):

kubectl -n miot-harness create secret generic harness-datasource \
  --from-literal=dsn='postgresql://harness:<password>@<pg-host>:6432/citus'
kubectl -n miot-harness create secret generic harness-anthropic \
  --from-literal=api-key='<anthropic-api-key>'
kubectl -n miot-harness create secret generic harness-langfuse \
  --from-literal=public-key='pk-lf-…' --from-literal=secret-key='sk-lf-…'

Troubleshooting

/health reports datasource.enabled: false despite a configured DSN

The provider’s freshness gate refuses to register data tools if the snapshot is older than the refuse threshold (nexo profile default: 240 minutes; override via datasource.freshnessRefuseMinutes). Possible causes:

  1. The upstream team hasn’t refreshed the materialized views recently.
  2. Wrong DSN — the harness reaches a stale read replica.
  3. ACL — the harness PG role lacks read on the freshness probe.

Check kubectl logs for the provider’s boot entries; they enumerate the failure mode.

Every auto-mode request returns 500

The intent router runs first on each auto request and defaults to a claude-* model. A missing/invalid ANTHROPIC_API_KEY therefore breaks all auto-mode traffic, not just data questions. Verify the key Secret exists and is mounted:

kubectl -n miot-harness exec <pod> -- printenv | grep -c ANTHROPIC_API_KEY

Tenant-gate refusals in the logs (not 500s)

datasource.tenantLock (or the profile default) must match the tenant id the front door injects via X-Miot-Tenant-Client-Id. If the front door sends the org client-id while the lock holds the org slug (or vice versa), every data request is refused. Align the lock with what the front door actually sends.

Pod crashes at startup after enabling auth

auth.enabled: true requires all of auth.issuer, auth.jwksUrl, auth.rs256Audience — the lifespan fails fast otherwise. The same fail-fast applies to an empty-string datasource.tenantLock or identity.signingKey.

Pod crashes on first /runs invocation with “read-only filesystem”

The container runs with readOnlyRootFilesystem: true. The chart mounts a workspace volume at /app/.miot-workspace; the harness writes run_store JSON there. If you’ve overridden securityContext or volumeMounts in a way that removes the workspace mount, the harness will crash on first write.

Verify with:

kubectl exec -n miot-harness <pod> -- ls -la /app/.miot-workspace
# should be writable by UID 65534

networkPolicy.enabled=true but Pods can’t reach Anthropic / OpenAI

Two common causes:

  1. CNI doesn’t enforce NetworkPolicy. Some Flannel modes ignore policies entirely. Verify with kubectl get pods -n kube-system | grep -E 'cilium|calico|antrea'.
  2. Transparent egress proxy. The chart’s NetworkPolicy permits the destination IP, but the proxy denies the hostname. Audit the egress proxy config.

If the symptom is “Pods can reach Anthropic but not the datasource DB”, check networkPolicy.coordinador.cidrs — empty means no rule is rendered (intentional fail-closed).

Upgrading

helm upgrade harness microboxlabs/miot-harness \
  --namespace miot-harness \
  -f values.yaml

Upgrading 0.2.x → 0.3.0 is a values break — see Migrating to 0.3.0. Pair the chart upgrade with a harness image containing modulariot#604; mixing old chart + new image (or vice versa) leaves the renamed env vars unread.

Uninstalling

helm uninstall harness -n miot-harness

Note: the chart-managed credentials Secret and the workspace PVC (if persistence.enabled=true and no existingClaim) are deleted. Back up run_store data first if it matters.
